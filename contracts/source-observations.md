# Source observations — v1, development code released

A receipt, statement line and bank transaction may describe the same purchase with different dates, signs and account vocabulary. A source observation records what its document says. A canonical transaction records the app's current transaction fact. A relationship between them is separate evidence; importing a receipt must not fabricate a bank match or add the expense again.

This contract extends the existing composition direction. It does not add a page endpoint or a fifth tool. The proposed collection is observations; the proposed import format is source_observations under existing import_preview/import_commit. The executable catalog/core expose both; development v0.5.28 includes this unit. Production remains the reference dashboard. The cloud ledger does not yet contain the privately staged original observations. Scoped core review and synthetic actual HTTP/stdio import/query/replay tests pass locally. Private extraction staging, rendered inspection and deployed client verification remain required before delivery.

## Data and ownership

L5 owns observation validation, immutable identity, relationships and pure projection. L2 faces authorize, validate envelopes and dispatch; storage persists the same ledger document with revision/CAS. Extractors parse and declare source custody; they do not certify source completeness or settle relationships.

An import envelope identifies source_id, source_type, source_hash, observed_at and extractor name/version. Each observation identifies its physical source_line/source_end_line and original record ID when present, preserves original fields, and separately declares normalized fields with their transformation. Source types retain Era, Statement, Receipt and Snapshot meanings. Hashes are declared custody until independently verified against bytes; a Snapshot remains derivative.

Observation identity is the tuple source_id/source_line. Source IDs identify an immutable document revision, not an account or merchant. A corrected document receives a new source identity and an explicit supersession edge; it never overwrites a previous row. A source registry binds each source_id to one immutable source_type, source_hash and extractor custody declaration across every line and later batch. Conflicting document metadata rejects the entire import, even when the conflicting line is new. A source correction uses a new identity and an explicit supersession edge. Original fields remain data, including any text that looks like instructions. Rendering uses text and approved links; extraction does not execute document instructions.

Normalized dates must carry their meaning, such as receipt date, purchase date or posting date. Amounts retain currency and sign convention. Original lexemes remain available. No implicit currency conversion or date/sign rewriting is allowed to satisfy canonical merge constraints. Unsupported or ambiguous normalization stays unresolved rather than choosing a convenient interpretation.

## Relationships and measures

A candidate relationship names source observation and canonical transaction identities, origin/evidence and actor custody. A legacy ledger link may seed a candidate, never an accepted match. Candidate identity is the tuple observation identity, target transaction identity and relationship kind. Exact duplicate candidates replay without extra rows; conflicting declarations for that tuple reject the batch. The source observation must exist or be created in the same valid batch. An absent canonical target is retained as an explicitly unresolved target reference, excluded from linked/attributed counts; it must not fabricate a transaction. Imports cannot set accepted/rejected review status or create a human-review event. Exact receipt ID/date/amount agreement with historical context supports extraction lineage; it does not certify bank reconciliation, account ownership or a curated fund/category label.

Observation amounts are non-additive evidence. They do not enter spending, payroll, reimbursements received, card settlements, budget commitments or debt balances merely because an observation was imported. The existing canonical measures remain unchanged. An explicit future relationship-review contract must define acceptance, rejection, amount/date relationships and append-only human events before accepted matches can be claimed. That command is outside this first import unit and is not silently implemented through a generic decision write.

Queries compose source type/identity, original record ID, normalized date and candidate transaction filters with bounded deterministic pagination. Pure evidence summaries distinguish original observation counts, canonical records, candidate links, accepted links and unresolved records. They preserve selected source-date semantics independently of bank posting dates. Candidate links do not establish Home/Work attribution. Without an explicit authoritative observation-purpose decision or a future accepted relationship that defines attribution, the observation remains unresolved. Combined shows unresolved observations separately; Home and Work summaries report the unresolved count separately from attributed observations and never borrow a candidate target’s purpose. A parent split across scopes remains mixed/unresolved until an explicit allocation is approved; no whole-receipt inheritance. All observation sums remain labeled non-additive source amounts, even after attribution. Counts never certify a complete account/month.

## Atomic import and export

Preview validates the entire batch without writes and reports new observations, exact replays, candidate relationships and conflicts. Commit requires authenticated transport actor, revision and idempotency key. Exact same-key replay changes nothing; changed content for a source tuple or committed idempotency key rejects the whole batch. A fresh key records a new immutable custody receipt and revision even when all source facts replay; this preserves the new actor/time without duplicate evidence or financial effects. Receipts include both observation lines and candidate identities, including candidates added against previously stored lines. A stale or invalid import preserves canonical facts, immutable source rows, observations, decisions and review history. Export includes observations and relationship custody alongside the existing ledger.

Limits must be declared in the executable schema/docs and enforced before mutation. Choose bounded payload, original-field depth/size and row limits during implementation, then test both the boundary and rejection cases. This draft deliberately does not advertise unenforced limits.

## Proposed first executable slice

These requirements are implemented locally and remain under scoped review; deployed clients cannot rely on them yet. The first envelope is `evidence: {source_id, source_type, source_hash, observed_at, extractor: {name, version}, supersedes_source_id?, observations, candidates}` with format `source_observations`. Reject unknown fields at every typed level. Document custody is `declared` until a byte-verification operation exists; callers cannot import a verified flag. Extractor version and name are nonempty strings. No source-purpose field or authoritative relationship-review state is accepted in this slice. Optional `supersedes_source_id` names an existing observation-source registry entry with a different source_id; it is immutable document metadata. A new source can supersede only an already stored source, preventing cycles and dangling edges. Exact replay preserves the same edge; changed supersession rejects the batch. The edge records a declared correction, never deletes old observations or settles bank relationships.

Each observation has integer `source_line` and `source_end_line` (one-based, end at least start), optional `original_record_id`, `original_fields` as a flat map of CSV/document field names to original string lexemes, and optional `normalized` fields. The exact optional `normalized` object has only `date?: {value, meaning, transformation}` and `amount?: {cents, currency, sign_convention, transformation}`. Date value is an actual YYYY-MM-DD calendar date with meaning `receipt|purchase|posting`. Amount cents is a safe integer, currency is an uppercase three-letter code, and sign_convention is `charge_positive|debit_negative`. Each present nested object requires every listed field, including a nonempty transformation string; reject unknown/orphan fields. An absent or empty normalized object is valid and records no normalization. Missing date or amount remains absent, never zero or today. This first slice deliberately supports flat original fields; nested document structures require a later explicit schema rather than unbounded arbitrary JSON.

Each candidate has integer `source_line`, `target_transaction_id`, `relationship_kind: describes_transaction|funding_candidate` and nonempty evidence text. Its source identity comes from the envelope. The server records the authenticated import actor and import receipt; a caller-supplied actor is forbidden. Query resolves current target existence without rewriting the original declaration. Candidate existence is distinct from acceptance, and funding candidates never count as purchases or income.

Local enforced hard limits: 500 observations and 1,000 candidates per batch; 100 original fields per observation; 100 characters per field name; 20,000 characters per original value; 300 characters per identity; 2,000 characters per candidate evidence/transformation; 1 MiB UTF-8 encoded evidence envelope. Physical line numbers must be positive safe integers. Reject reserved object keys at every map boundary. Source hash must be lowercase SHA-256; observed_at must be an explicit UTC timestamp. L5 validation enforces these limits and local docs publishes source_observation_limits. The transport envelope remains generic evidence; nested executable JSON schema is published for source_observations through the import condition and docs. Exhaustive boundary tests remain owed. Do not rely on a transport's body limit as domain validation.

Observation query uses source_id/source_type/original_record_id/month or explicit months (1–24) and offset/limit (maximum 200), with deterministic source_id/physical-line ordering and a full-match count. Month means the declared normalized source date; records without one remain available through an unfiltered query. Month and months are mutually exclusive; an unfiltered source-date query includes undated records. No canonical merchant, account or scope is inferred. The inspector displays unresolved source records across Home/Work, explicitly separated from attributed financial counts. Pure summaries expose source-type counts, unresolved attribution counts and candidate target availability; accepted match count remains zero until a reviewed relationship contract exists. Complete ledger export preserves the new registries automatically; dashboard snapshot compatibility export must not be advertised as complete evidence export.

Delivery order: implement the pure validator/planner/query with synthetic tests; wire existing imports and query collection in core and the executable catalog; prove actual HTTP/MCP replay and conflict parity; stage the original giving CSV through a private extractor; add an evidence inspector that renders core results; independently review and verify the rendered inspector before Git-connected development release. Existing financial projections and user decisions must remain byte-equivalent throughout the import test.

## Evidence required before delivery

- Synthetic receipt/posting-date and opposite-sign cases preserve both sources and create only candidate links.
- Exact replay, changed-source conflict, conflicting source hash/type/custody on a new line, changed-idempotency body and stale revision leave all state unchanged as specified.
- Candidate duplicate/conflict, missing target and attempted accepted-status import obey referential and review boundaries.
- Receipt imports add zero canonical spending or income; existing decisions and reviewed classifications survive.
- Unlinked observations, mixed-scope parents, currency mismatch and missing normalization stay explicit.
- Core, authenticated HTTP and actual MCP protocols agree on import/query/export effects and pure projections.
- A real-source staged extraction preserves bytes/hash/physical line ranges, original fields and transformation provenance; no private source enters Git.
- Rendered evidence explains source observation versus candidate bank link in user language, at phone and laptop widths.

Planning perspectives: product preserves financial clarity without false matches; design separates original fact, curated label and relationship state; QA targets replay/conflict/date/sign and mutation recovery; Terry traces existing import authority and human review boundaries; vodka keeps finance semantics in L5 and reuses the declared service surface. These are planning considerations, not formal lens passes or a new house rule. Scoped reviews and current lens prerequisites remain owed before delivery.
